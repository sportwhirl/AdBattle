# URSA tiny staging draft

This is an **offline, private quality experiment**. It cannot create a site ad,
write to Supabase, upload media, change wallet balances, or publish a video.
The existing 10-second Luma job scaffold and the image publication gate remain
separate. Video posting still requires its own full-media safety, duplicate,
private-storage, verified-copy, and moderation workflow.

## Why this setting

On a GeForce RTX 5090 Laptop GPU, the pinned URSA-0.6B-FSQ320 model made a
256×160, 17-frame sample in **14.648 seconds after warmup** at 50 steps, with
3.294 GiB peak PyTorch allocation. The 320×192 alternatives took 24.382 and
38.997 seconds and looked less coherent for the single tested sprout prompt.
Two warmed tiny jobs took 31.608 seconds together, compared with 29.296 seconds
for two sequential warm generations. The two copies fit in 11.283 GiB of GPU
memory but did not improve throughput. These are one prompt, one seed, and two
timings per case on a laptop GPU, not a production throughput or quality claim.

The original benchmark repeated 17 source frames, causing a strong jump at the
loop boundary. This script plays frame indexes `0..16,15..1` at 8 fps. That is
exactly 32 frames and four seconds, with adjacent frames at the turn and seam.
On the sample, the decoded boundary difference dropped from approximately
39.7 to 7.4 mean RGB levels at its native resolution. Reversed motion may be
obvious in other scenes, so inspect the actual result. The 256×160 source is
preserved; the preview and poster center-crop eight pixels from the top and
bottom to fit a 256×144, 16:9 card. There is no portrait mode yet.

## Run on the CUDA machine

Use the existing tested `ursa-bench-venv` with PyTorch, URSA at commit
`68ed282b0ed788cf02d0cc615ef2a8b96c855dba`,
`transformers==4.57.1`, `diffusers==0.35.2`, NumPy, FFmpeg, and ffprobe.
The model is pinned to revision
`2440a09773270ad8ff1f11ba02185a48c5e9de30` and will use the cached
weights from the benchmark. From the repository root:

```sh
mkdir -p -m 700 "$HOME/adbattle-private-video-drafts"
# Put one 12–600-character creative prompt in a private UTF-8 file.
~/ursa-bench-venv/bin/python scripts/generate_ursa_tiny.py \
  --prompt-file "$HOME/adbattle-private-video-prompt.txt" \
  --output-dir "$HOME/adbattle-private-video-drafts/draft-001"
```

The new directory contains `source.mp4` (the 17 original generated frames),
`preview.mp4` (silent, four seconds, 8 fps, 16:9), `poster.jpg`, and
`manifest.json` with checksums and the seed. The prompt is never printed or
copied into the manifest. The directory is private (mode 0700) and is
published atomically without replacing an earlier draft. You may supply
`--seed` to reproduce a draft. All three media files have size caps and are
checked with ffprobe before the draft directory appears.

Concurrent invocations using the same local state directory wait for the
exclusive CUDA-0 lock. The default wait is ten minutes, adjustable with
`--wait-seconds`; this is a **local process lock**, not a durable site job
queue. Separate hosts, unrelated GPU programs, or invocations using a
different `--state-dir` are not coordinated. Each invocation loads the model,
so the benchmark's 14.648-second warmed inference time is not its first-draft
response time. A persistent one-worker-per-GPU service and durable queue would
be needed before user-facing creation.

## Review and next gate

Check the whole four-second preview and its turn, crop, loop seam, and prompt
adherence across several kinds of prompts and seeds. The tested sprout sample
had a recognizable subject but a cluttered background and was not fit to use
as a public ad. Do not treat this local artifact or its poster as content
approval. Keep all generated bytes private until the complete video scan and
verified publication flow exists.

Run the offline encoder and lock checks with:

```sh
python3 -m unittest discover -s tests -p ursa_tiny_staging_test.py
```
